# Monitoring approach review — 3 October 2026

Original read-only review of candidate monitoring and its delivery/scoring paths. Follow-up implementations are recorded in RELIABILITY.md; the findings below describe the pre-fix snapshot. Risk/incident aggregation was explicitly excluded from the follow-up. No monitoring behavior was changed in this review. The previous camera update's 17 regression checks passed; those checks are not a real-device accuracy or load evaluation.

## Fix first

1. **Alert delivery loses failed Python-to-Electron events** (`ai-module/main.py:22–31`). The worker logs a failed POST and permanently removes the event. Electron's disk buffer only protects events that reach Electron. Persist before acknowledgment, preserve the original timestamp and event ID, and retry failures. Prefer enqueueing durably at the local receiver before waiting for a remote upload: currently `electron/ipc/pythonBridge.js:130` attempts the backend first, which makes the single Python delivery worker wait on network/storage latency.
2. **Allowed-app file policy equates age with misconduct** (`ai-module/whitelist_enforcer.py:646`, `:680`, `:693`). A document modified before the exam can be a legitimate template/reference; a cheat sheet modified during the exam can pass this heuristic. Recent shortcuts also do not prove a document is currently open. The response can terminate all Word/VS Code instances (`:735`), risking unrelated unsaved answers. Define teacher-permitted files/directories and confirm the specific offending process before enforcement. Keep uncertain observations reviewable instead of closing every matching application.
3. **Object detections compete with one another** (`ai-module/ai_monitor.py:774`). Only the top-scoring phone/book detection is tracked, and alternating winners reset the counter. Also, class continuity is used without matching object location, so unrelated boxes can accumulate. Track repeated evidence separately per class and match nearby boxes. Use aspect-preserving letterboxing instead of stretching each webcam frame to 640x640 (`:742`), with corresponding coordinate conversion and regression checks. Actual model metadata confirms YOLO26n, COCO, end-to-end output `[1,300,6]`; no additional NMS is needed for this export. Headphones are not among its trained COCO classes.

## Improve after a measured comparison

4. **Voice architecture is reasonable; threshold calibration is missing** (`ai-module/voice_monitor.py:435–502`). WebRTC VAD gates speech before Resemblyzer speaker comparison, using normalized embeddings and two mismatches. A single 0.75 cutoff is not a validated decision boundary for this laptop, room, language or microphone. Add a measured uncertain range and compare candidate/other-speaker recordings before changing the cutoff. An unfamiliar embedding is not proof of a second live person: played audio, mixed speakers and changed speaking conditions can affect it. Two three-second windows mean sustained unfamiliar speech generally needs around six seconds plus processing; short remarks can deliberately be missed.
5. **Some invalid voice segments preserve previous mismatch state** (`voice_monitor.py:443`). Returning when preprocessing leaves under one second does not clear the prior mismatch. A later segment can complete a count across an unusable observation. Define consecutive valid segments explicitly. The capture loop also suppresses read errors (`:366`); expose the exception and recover the input device rather than only relying on a stale-audio health check.
6. **Camera obstruction is a useful heuristic, not an obstruction classifier** (`services/lighting_occlusion_detector.py:48–72`). Whole-frame brightness and standard deviation cannot reliably separate darkness, obstruction and exposure changes. A bright uniform cover above the 180 cutoff escapes the obstruction branch, though missing-face monitoring can still alert. Keep the combined label and examiner review, use a monotonic timer, and evaluate lighting/partial-cover examples before introducing relative baseline thresholds. Current variable named variance actually stores standard deviation.
7. **USB polling is appropriate but has blind spots and latency** (`usb_monitor.py:44`, `:128`). CIM filters `InterfaceType == USB`; verify USB SSD/UASP devices on the target laptop rather than claiming all external storage is covered. Polling every three seconds plus launching PowerShell/performing CIM means alerts are not instantaneous and very short attachments can be missed. Event notifications or a persistent WMI subscription are alternatives only if measurement justifies their complexity. No AI model is needed for this feature.
8. **Risk is a prioritization index** (`server/src/services/scoring/DecayScoringStrategy.js:24`, `server/src/scoring/severityEngine.js:21`). Recent and cumulative severities give an explainable heuristic, not a calibrated probability of cheating. Normal pending events affect it; dismissed events and pending late evidence are excluded. Head/object alerts can repeat for one continuous incident and inflate the cumulative floor. Consider incident aggregation while retaining evidence, and make pending vs confirmed counts clear. Avoid presenting a score of 80 as an 80% cheating probability.

## Library recommendations

- Keep YOLO26n ONNX Runtime: the model/output format fit the current object pipeline. Fix preprocessing and temporal association before swapping models. Official reference: https://docs.ultralytics.com/guides/end2end-detection
- Keep Resemblyzer initially and evaluate recordings. Its maintainers describe speaker verification through embedding similarity and note strongest support for English: https://github.com/resemble-ai/Resemblyzer
- Compare Silero VAD only if WebRTC VAD actually misses speech or gates noise in the recorded room. Its ONNX version can use the existing ONNX Runtime, but it solves speech detection rather than speaker identity: https://github.com/snakers4/silero-vad
- Keep native Windows/CIM and psutil for USB/process checks. Windows documents multiple disk interface types: https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-diskdrive
